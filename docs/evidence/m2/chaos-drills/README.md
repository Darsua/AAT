## Observed Discrepancies & Operational Findings

1. **`schema` (`tester-agent` -> `mock-bmkg:8081`, [02-schema.log](02-schema.log)):**
   - `tester-agent` resolves `role=mock` services alphabetically (`mock-bmkg:8081` ahead of `mock-pvmbg:8082`) and omits `PVMBG_TOKEN`; `contracts/pvmbg.yaml` defines authenticated `POST /admin/schema-version` exclusively on `mock-pvmbg:8082`.
   - Cross-node `hostNetwork: true` traffic from `tester-agent` traverses the Flannel VXLAN interface (`10.42.x.0`) rather than node eth0, which `kube-router` rejects under `allow-mock-admin-policy`.
2. **`partition` (`tester-agent` `iptables` resolution on Debian 13, [05-partition.log](05-partition.log)):**
   - Debian 13 (`trixie`) symlinks `/sbin/iptables` and `/usr/sbin/iptables` to `/etc/alternatives/iptables` -> `/usr/sbin/iptables-nft`; inside `tester-agent`'s `/host` bind mount without `chroot /host`, the absolute symlink dangles so `block_internode` exits immediately (`biner iptables tidak ditemukan di host`).
3. **`wipe-node` VM poweroff, single-broker availability, & store wipe behavior ([06-wipe-node.log](06-wipe-node.log)):**
   - **QEMU unit restart policy:** Host systemd units `aat-aqua.service`, `aat-ruby.service`, and `aat-akane.service` previously configured `Restart=on-failure`. A clean guest `poweroff` (`ACPI S5`) causes `qemu-system-x86_64` to exit `0/SUCCESS`, leaving `ruby` off until updated to `Restart=always` and started (`ConfigMap tester-agent/tester-run` with `status="go"` and `coordinator="ruby"` also had to be deleted once so `tester-agent-rgrbm` stopped re-triggering `wipe_and_shutdown` on every boot).
   - **Mid-outage degradation when `ruby` went offline:** Because `redpanda-0` (single-replica Kafka broker) is pinned to `ruby` (`k8s/base/broker.yaml`) and `aggregator`'s `/health` readiness probe (`services/aggregator/internal/api/health.go`) checks `BrokerPinger.PingBroker`, losing `ruby` caused all surviving `aggregator` pods on `aqua` and `akane` to become `0/1 Ready` (`HTTP 503`), temporarily returning `503` on `/internal/audit/checksum` and `500` on `/api/v1/hazards` until `ruby` and `redpanda-0` returned. Surviving `aggregator` pods also logged `begin lease tx: context deadline exceeded` while `store-ruby` packets dropped silently during node down-time. Additionally, `coredns` (1 replica) was initially on `ruby` until Kubernetes evicted and rescheduled it to `aqua`.
   - **Host store path & log notes:** Because `TESTER_HOST_STORE_DIR` is unset in the upstream `tester-agent` DaemonSet manifest, `/var/lib/bnpb-store/store-ruby/pgdata` remained intact after `wipe_and_shutdown`; a live `TRUNCATE TABLE hazards, dlq_messages` on `store-ruby-0` (`bnpb_shard_2`, `bnpb_shard_1_r1`) verified automated `SyncShardReplicas` recovery from `store-akane-0` (`bnpb_shard_2_r1`) and `store-aqua-0` (`bnpb_shard_1`). Note that the unmodified raw log's line 1 header comment mislabeled the scenario target as `akane / store-akane-0`, and lines 106–107/133–134 captured a `kubectl logs --field-selector` flag error leaving the replica-sync log excerpt empty (convergence was proven by direct per-shard SQL counts and Audit checksums), while three consumer pods remained in `CrashLoopBackOff` at `16:10–16:11 UTC` before recovering cleanly by `16:14:13Z`. Subsequent readiness hardening separated Aggregator's readiness probe to `GET /readyz` (`k8s/base/aggregator.yaml`) so a single-broker outage does not mark surviving Aggregator replicas unready.
